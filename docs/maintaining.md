# 文档维护

这些文档帮助维护者快速定位事实、判断证据。`docs/` 中的公共技术文档和根目录 `AGENTS.md` 随仓库维护；本地专用说明、内部原始资料与临时产物由 [`.gitignore`](../.gitignore) 排除。本地专用说明使用精确文件规则，不整体忽略 docs。公共文档只保存可复用的技术事实，不保存个人会话、用户工作内容或本机私人路径。

维护直接在 `develop` 进行。改动后同步相关文档，纯维护只递增 `dev.N`；正式发布仍需单独授权。

## 内容放在哪里

| 内容 | 主位置 | 更新时机 |
| --- | --- | --- |
| 安装、设置、首次连接 | 根目录中英文 README | 用户安装方式或运行前提变化时；两种语言保持一致 |
| 使用者隐私、使用约定与联系入口 | 根目录中英文 PRIVACY / TERMS 文件 | 数据流、保留方式、权限、维护主体或条款变化时；双语同步并随安装树保留 |
| 开发与正式版本、递增和同步检查 | [versioning.md](versioning.md) | 版本治理或交付检查变化时 |
| 尚未发布的影响及正式版本摘要 | [英文 CHANGELOG](../CHANGELOG.md) / [中文 CHANGELOG](../CHANGELOG.zh-cn.md) | 两份按条目同步；本批使用者影响变化时归并，正式交付前准备版本条目和计划日期，交付后只读核验实际状态 |
| 系统职责、消息流、连接/超时、部署配置 | [architecture.md](architecture.md) | 对应实现或配置变化时 |
| 版本身份、功能结果与限制 | [sdk/README.md](sdk/README.md)及构建页 | 得到新构建或新对象的可核验证据时 |
| 复验流程、字段、验收模板 | [sdk/verification.md](sdk/verification.md) | 新证据暴露了通用记录或验证缺口时 |
| Agent 执行任务的短入口和已验证配方 | 随包 [Skill](../skills/affinity-mcp/SKILL.md)及 references | 已验证的新规则需要随插件交付时 |
| 本地 Agent 导航 | [agents/domain.md](agents/domain.md) | 文档入口或实际领域边界变化时 |
| 三平台文档 hooks、隐私检查及复核 | [hooks.md](hooks.md) | hook 行为、平台启动或回归范围变化时 |
| 问题、待办和验收 | 本地 tracker（仅内部） | 按已有 issue 查重、更新 Comments；不在架构页复制完整待办，也不从 docs 链接个人工作记录 |
| 调查资料与过程 | 本机忽略区（仅内部） | 采用的结论归入相关技术说明；长期架构决策按 ADR 约定记录，不引用本地调查资料 |
| 个人会话分析与原始复核 | `.scratch/<effort>/archives/` | 仅本地保留，公共文档不得引用；移动时同步修正目录内部引用 |
| 实验原始输入输出 | `.scratch/<effort>/evidence/` | 新实验追加；不静默重写历史观察；不得被 docs 直接引用 |

同一事实选一个主位置。导航、Skill 或摘要可以简短转述并链接，避免每个文件各维护一份完整能力清单。

开发文档、测试及公开验证夹具由 `develop` 维护；生产分发按[具体文件允许清单](versioning.md#production-content)核对。资源可公开或位于 `assets/` 不代表它属于安装内容，生产候选及安装副本均不能混入开发证据。发布范围的修订也先在开发分支完成。

## 写法约定

1. 开头写用途和适用范围；实现事实绑定源码或提交，SDK 功能证据注明观察日期和构建。文档编辑日期只留在本机记录中。避免没有日期/构建限定的“当前支持”“永远不支持”。
2. 技术事实链接到实现文件、固定提交、官方资料或原始证据键。源码行号只是定位提示；更新相关源码后重新核对，不能只保留失效行号。
3. 清楚区分事实、历史转录、建议和未验证项。文档存在、工具可见、命令可构造与目标完成不是同一个状态。
4. 标题按读者要解决的问题组织。表格用于能力/版本比较；小型架构图用 Mermaid，并在正文交代边界。不要为套模板新增没有内容的章节。
5. 仓库内导航用相对链接；外部资料链接到一手来源。本机日志路径、会话标识、个人工作内容、个人本地时区及偏移和原始回包只留在本地归档，不进入 docs，也不作为能力结论的链接来源。公开观察、验证与交付日期按 UTC 日历日写为 `YYYY-MM-DD`，不含具体时刻。此要求不限制 Git 作者时间或提交者时间的偏移。机器协议、时长、版本/历史身份及私有证据保留各自格式；正文扫描不检查 Git 元数据。
6. 新增/修改文本使用 UTF-8 无 BOM。随仓库维护的文件按用途命名，文件名和正文不保留代理专用前缀。仓库内的临时脚本、快照、备份和派生取证附件放在 `.scratch/`，按工作目录和资料用途组织，不纳入提交；不要改名或删除用户或工具既有资料来满足命名规则。
7. **docs 不得引用被 Git 忽略的内容。** 链接、图片、引用式链接、HTML 资源以及具体证据路径都适用；仓库内目标必须存在且可纳入 Git。忽略区的原始资料先整理成可公开的脱敏技术摘要。可以说明内部目录的用途，但不能让文档阅读或事实核验依赖其中的具体文件。检查使用 `git check-ignore --no-index`，不能因文件已被强制跟踪就绕过忽略规则。
8. 忽略规则覆盖本地 Agent 状态、内部资料、Node 依赖与运行产物、环境配置及系统/编辑器杂项。环境配置模板可纳入 Git，提交前确认只含示例值；共享项目配置和公共文档按文件职责维护，不笼统忽略工具目录或源文件类型。
9. **所有 Git 提交的标题与正文统一使用英语；若以后使用 PR，其标题、说明和最终 squash 信息也使用英语。**

## 能力与平台表述

- MCP/SDK 能力按操作和当前运行时条件描述，默认共用同一套配方；不要因为只在某个系统实测过，就写成 Windows 或 Mac 专用能力，也不要给 Agent 设置系统白名单。
- 实测平台、构建、日期和失败结果作为证据元数据保留；未在其它系统复验，不等于禁止使用，也不等于跨平台验收已完成。
- 只有官方明确限制或相同前提下确认的差异，才写系统限制并链接依据；单次失败不得直接归因为操作系统缺陷。版本、权限、参数、对象和后置结果分别核对。
- 确有差异的安装路径、启动方式、快捷键和宿主要求可按系统说明。保留历史原始身份，功能标题、README、更新日志和随包指引不得把证据平台误写为产品支持范围。

## 版本与架构决策

文档编辑日期、变更与检索过程、本机测试流水及工具启用/信任状态仅保存在本机的 Git 忽略区，不纳入提交、不推送。docs 不保存或引用这类记录，无论它们写成表格、段落还是页尾说明。公开文档保留使用方法、测试范围、架构决策，以及 SDK 功能证据所需的观察日期、构建号、样本结果与验证边界。

**每批开发交付前必须递增开发版本，不要等用户提醒。** 完整规则见[版本与变更日志](versioning.md)：`develop` 日常用下一正式目标的 `-dev.N`。正式交付先在 `develop` 转正、检查、审查、提交并推送，再把该确切提交里的生产内容同步到 `main`；同步后保留正式版本，下一批开发再开始新的 `dev.1`。代码、配置、Skill/references、公共文档、测试和维护工具都算开发批次；同一批的修改、验证和复审只更新一次版本。纯维护交付只增长开发编号，不因一次文档或测试修改就发起正式发布；正式目标只按累计产品交付影响和发布授权决定。

**版本号和所有现行版本声明，只放在本批最后一个实现 commit 中。** 先完成适用检查和独立审查，再按用户授权组织提交，并核对最终提交与已审内容一致。若还要追加实现修正，先调整提交顺序，保持版本变更仍在最后一个实现 commit；规则本身不授权 Git 操作。实际推送 `develop` 后，[日期收尾](versioning.md#development-date-closure)只移动双语日志的当前开发条目：版本不变，不增加 `dev.N`，不改已交付提交。真实日期取证和两次远端读回完成后，才算完整交付。

版本更新必须同步核对以下位置，不能只改一份清单：

- [Codex 插件清单](../.codex-plugin/plugin.json)、[Claude Code/ZCode 插件清单](../.claude-plugin/plugin.json)及[共用市场条目](../.claude-plugin/marketplace.json)。
- 代理的 `clientInfo.version` 与 `serverInfo.version`；源码位置见[架构说明](architecture.md)。
- [文档入口](README.md)、[架构说明](architecture.md)、[SDK 版本身份表](sdk/README.md#version-identity)和根中英文 CHANGELOG 的现行版本标题；待交付候选位于英文 `Unreleased` / 中文“未发布”，已交付版本位于实际日期分组。根中英文 README 的渠道说明保持一致。

插件版本、MCP 协议日期与 Affinity 应用构建号分别维护；历史构建页、脱敏证据及既有观察中的应用、协议和真实运行身份保持原值。明确授权的源码重编号可以更新对应的源码身份与固定链接，但须标明仅为身份映射，不能改写实验日期、结果或补填当时加载的安装版本。更新仓库版本不表示已提交、推送、发布或刷新安装副本，这些状态仍需分别核验。

版本摘要集中在根中英文 CHANGELOG，按日期、版本和对应语言的分类分层，不在 `docs/` 追加工作流水。未交付的开发候选放在英文 `Unreleased` / 中文“未发布”下；没有待交付内容就删掉该分组。已交付的开发和正式版本使用各自首次实际交付的 UTC 日期。正式候选先在 `develop` 整理计划日期，再把同一套日志同步到 `main`，不在生产分支另补或转正。历史日期按已确认的实际交付事件补齐，缺证据时保留“日期待核实”，不用计划或 Git 日期代填。正式交付要求 `main` 只包含安装树及根中英文 CHANGELOG，不机械合并开发维护目录。

只有实际作出需要长期记住的架构选择时才新增 `docs/adr/NNNN-<topic>.md`。最小内容为日期、状态、上下文、决定、选项/权衡、后果和验证条件；已被替代的记录保留并链接新记录。当前架构从源码还原，不为未留痕的历史动机补写“已接受”的 ADR。[ADR 模板参考](https://adr.github.io/adr-templates/)。

## 交付前检查

- 按[两类版本检查](versioning.md#两类检查)分别核对静态同步和相对已确认基准的交付增量，明确本批候选与实际提交、发布状态；历史观察版本不变。版本号及所有现行版本声明仅出现在本批最后一个 commit 中。版本更新和必要验证完成后才能报告本批工作完成。
- 正式交付另按[生产文件允许清单](versioning.md#production-content)检查完整树及安装引用，清除生产候选中的开发资料遗留项；版本检查成功不能代替此项范围验收。
- 链接目标和证据键存在，代码行号与说明匹配；外部资料的产品/版本范围正确。
- 新旧构建结果并列保留；旧 reference 的未限定结论有差异说明。
- 操作有后置状态才标样本通过；只读反射和执行者视觉观察不冒充新写入或可重看截图。
- docs 的本地引用目标必须存在且不被 Git 忽略；检查实际生效的仓库、目录级和全局忽略规则。README/Skill 面向插件安装用户的引用还需核对安装包内容：Git 可跟踪不等于安装包一定包含。
- 隐私扫描覆盖整个 `docs/`（包括被 `.gitignore` 忽略的文件）；不得出现本机路径、运行时对象/会话标识或指向原始 `.scratch` 证据的 Markdown 链接。
- 逐份检查正文、表格和页尾，不只搜索“变更记录”标题；文档编辑、检索过程和本机验证流水不得混入公共技术说明。
- 文档修改通常检查链接、事实和编码即可；代理代码或启动配置修改才按影响运行对应回归，不为纯文字变更新建镜像实现的测试。
