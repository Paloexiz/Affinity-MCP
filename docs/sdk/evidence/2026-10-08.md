# 2026-10-08 脱敏 SDK 证据摘要

本页汇总 2026-10-08 的 SDK 样本结果和只读探针证据，结论仅适用于下述条件。匿名证据 ID 只用于在本页和构建记录中稳定引用，不映射到会话、文件或用户身份。

## 适用条件

- Affinity：`3.3.0.4850 Win32`；观察日期：2026-10-08。
- 仓库插件清单：`0.1.10`；独立 SDK 版本：未取得。
- 主样本是无业务内容的隔离、未保存文档，640 × 480 document pixels、96 DPI、1 页，包含普通文本、混排文本和小尺寸文本框。
- A-06～A-08使用另一份960 × 640 document pixels、96 DPI、1页隔离样本，包含一个艺术字对象和一个未链接文本框；均为通用测试文字。
- 本页不保存原始脚本、原始回包、运行时对象标识、会话标识、本机路径或个人工作内容。没有图片像素时，视觉结论只保留为执行时观察，不能由本页重看。

## 证据

### A-01：应用身份、入口和 Collection

只读探针确认了该构建的应用版本和平台。`DocumentApi.getDocumentProperties` 在所查入口为 `undefined`；`app.userDesktopPath` 有 getter，但应用模块顶层同名导出没有可用值；`UnitType`、`DocumentCommand` 不在脚本全局作用域。`Collection.of(1, 2)[0]` 为 `undefined`，`.first` 与 `.at(0)` 返回首项。

这些结果只约束所查入口和对象，不证明同名功能在所有 native 模块或未来构建中不存在。

<a id="a-02"></a>
### A-02：文本替换和溢出

当前 `Node.setText` wrapper 使用 `TextSelection.create(this.storyRange)`。普通文本完整替换在隔离样本上读回通过；20px/12px 混排文本替换后合并成单一 20px run，因此普通替换不构成保留混排格式的通用配方。

`canHideOverflow` 在所查 wrapper 中是 getter。小尺寸文本框的 Story 字符仍完整存在，已有执行观察显示文字溢出框外；这不足以证明隐藏状态已经打开，也不能据此推断永久丢字。改字后的行数、runs、框尺寸和可见范围仍需逐项验收。

### A-03：同步关闭

对隔离未保存样本调用同步 `Document.close()` 后重新枚举文档，目标样本消失。该结果只覆盖同步路径、该构建、该类隔离样本和该后置检查；`closeAsync`、promises close、带未保存业务文档及其他平台仍未验证。

### A-04：文字节点、文本流与 Align 只读入口

观察日期与构建同上：2026-10-08，Affinity 3.3.0.4850 Win32。读取SDK的`nodes.js`包装器时，确认两个创建入口的签名分别为`ArtTextNodeDefinition.createFromStoryBuilder(position, storyBuilder)`和`FrameTextNodeDefinition.createFromStoryBuilder(frameBox, storyBuilder)`；这项证据只说明参数入口，实际创建样本见A-06～A-08。

`commands.js`包装器包含`DocumentCommand.createLinkTextFrame(srcNode, destNode)`和`DocumentCommand.createUnlinkTextFrame(node)`；只读成员枚举也列出这两个公开命令。相关原生`DocumentCommandApi`原型链中可见`createLinkTextFrameCommand`和`createUnlinkTextFrameCommand`。这些观察没有执行链接/取消链接，不验证文本流范围、内容保留或撤销效果。

当前 wrapper 和已查 native 原型中存在水平段落 Align 相关入口，包括 `ParagraphAtts.alignXType`、`StoryDelta.createAlignX` 和 `DocumentCommand.createFormatText`；只读检查得到 9 个水平枚举成员。当前检查范围内没有找到框内垂直 Align 的对应读写入口。

这里的“未找到入口”是检查范围内的能力缺口，不是对整个应用功能的永久否定。移动文本框、改变框尺寸或做视觉居中也不等于设置原生垂直 Align。

水平Align的实际写入结果见A-07；A-04保留只读检查本身的证据边界。

框尺寸调整和自动refit仅收集到待测建议，没有本构建操作前后字号、文字缩放、框几何、排文和溢出的对照证据；不据此提供已验证的自动适配配方。

### A-05：错误、hints 与代理边界

观察资料日期为2026-10-08，同批应用身份探针确认`3.3.0.4850 Win32`。下列回包并非都自带独立精确时间或构建字段；实际运行的代理和宿主精确版本未完整记录，不能用当前仓库清单补填。A-05.4来自同日后续资料，其回包没有独立时间或构建字段，不能据此认定它是A-05.3同一请求的恢复或相同参数的重试。

| 证据 ID | 动作与实际返回 | 结论范围 |
| --- | --- | --- |
| <a id="a-05-1"></a>A-05.1 | 探针错误引用`affinity:document`；结果文本含`Error: Failed to resolve module affinity:document`，但`isError=false` | 探针输入错误，不是业务任务失败；false也不能证明脚本成功 |
| <a id="a-05-2"></a>A-05.2 | 使用无效文档身份调用渲染，返回文档不存在错误，`isError=true` | 预期负例，只证明这次无效身份被拒绝，不计作正常业务任务失败 |
| <a id="a-05-3"></a>A-05.3 | 一次`search_sdk_hints`等待超时；收到`-32603`代理错误，文本附检查应用启动与MCP设置的通用建议，`isError=true` | 同批另有成功SDK读取记录，不能根据该通用建议判定应用未运行；超时根因未确认 |

A-05.4中的refit与保持字号建议没有本样本的操作前后状态证据；水平枚举列表不完整，A-04记录了9个成员。将SDK垂直Align入口缺口推广成文字始终顶端排文、以水平FirstLineIndent解释垂直Initial Advance，均不能采作已验证配方。概念区别见[构建页](../3.3.0.4850.md#alignment)；实际水平写入结果只采用A-07的有限样本。

上述通用启动建议属于历史回包。当前仓库代理按故障阶段提供诊断，仅connect失败附连接检查建议；可能已提交的调用在超时后须先读回目标状态，不自动重放。当前传输行为以[架构说明](../../architecture.md#时间边界与恢复)、[代理实现](../../../scripts/affinity-mcp-proxy.mjs)和[代理回归测试](../../../scripts/affinity-mcp-proxy.test.mjs)为依据，不证明历史运行副本或用户已安装副本已更新。操作是否完成仍需同时检查内容与实际状态，不能只看`isError`。

### A-06：同一艺术字对象中的多行与混排

观察构建与日期同上。`StoryBuilder` 使用艺术字默认样式、`addText`与`addParagraphBreak`，再经 `ArtTextNodeDefinition.createFromStoryBuilder` 创建一个艺术字对象。全文包含三行中英文字，24px与18px字号runs并存；对象读回及执行时渲染均确认三行保持在一个 `ArtTextNode` 中。

通过显式文本子选区，将某个18px run内的三个ASCII字符作同长替换后，全文只发生预期变化，换行、字号runs和对象数量保持。它不证明任意长度或跨run替换能保留全部格式，也不改变A-02中整段混排替换失败的结论。艺术字多行无需以逐行、逐词创建对象实现；是否拆分应由语义块和独立变换需求决定。

### A-07：单框水平Left/Centre/Right写入

在400 × 220的未链接框中，通过 `Selection` 的实际文本子选区、`StoryDelta.createAlignX` 和 `DocumentCommand.createFormatText` 依次切换Centre、Right、Left，`ParagraphAtts.alignXType`读回分别为1、2、0。字号24px、文字缩放、全文和框几何保持，文字横向边界随模式变化；最终Centre的执行时渲染确认两行在框内水平居中。

这证明三种水平模式在该单框样本上可写，不覆盖其余六种枚举、链接框或部分段落作用范围。已查TextFrameInterfaceApi和DocumentCommandApi原型仍未发现相应原生垂直读写入口；水平写入成功不补足垂直接口缺口。

### A-08：框中心与内容中心的反例

新建框使用默认段落样式，水平属性为Left，文字出现在框的左上区域。框为 `(280,210,400,220)`，中心 `(480,320)` 恰好为页面中心；文字内容中心约 `(356.73,240.55)`，相差约123.27px和79.45px。

`getSpreadVisibleBox(false)`返回400 × 220的框边界；`getExactSpreadVisibleBox(false,false)`返回约151.30 × 61.07的文字边界，位置与执行时画面一致。因此框居中不能作为内容居中的证据；经核验的实际内容边界可以在不收紧固定框的情况下用于位置判断。

样本无描边、效果、裁切、嵌套变换或溢出，不能据此给出通用内容测量或自动fit公式。没有测试框尺寸调整，Left/左上观察也不代表所有模板或既有框的默认状态。水平Centre改变横向排文但未改变内容纵向位置；原生段落居中也不保证完整墨迹或字形主体的光学中心完全重合。

### A-09：多行段落居中与文字块水平定位

在同一构建的两个未链接、多行 `FrameTextNode` 上，先经显式文本子选区写入原生段落Centre，再调用 `curvesInterface.polyPolyCurves.getExactBoundingBox(baseToSpreadTransform)` 取得spread坐标中的字形轮廓边界，按内容中心差值做水平平移。该读取无需转曲、复制或修改轮廓。两个对象的字形中心横坐标读回一致，段落模式均为Centre；文字、字号runs、文字缩放矩阵、框宽高与上下位置保持，执行时渲染确认长短行的居中排文及块位置。

此前仅平移对象使合并外接边界中心一致时，段落Left保持，不能通过多行居中排版验收。段落内各行居中与文字块定位是两个可同时需要的操作，须分别检查。该样本的字形轮廓边界与exact visible边界一致，不推广到复杂效果、裁切、路径字、彩色字体、链接流或溢出文本；原生段落Centre也不承诺逐字墨迹的光学居中。未进行耗时基准或原生GroupTransform的Frame边界语义写测。
