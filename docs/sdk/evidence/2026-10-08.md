# 2026-10-08 脱敏 SDK 证据摘要

本页汇总 2026-10-08 的 SDK 样本结果和只读探针证据，结论只适用于下面列出的条件。匿名证据 ID 只在本页和构建记录中引用，不指向会话、文件或用户身份。

## 适用条件

- Affinity：`3.3.0.4850 Win32`；观察日期：2026-10-08。
- 对应重编号后的仓库源码标识：`0.1.0`。这只是源码身份映射；当时实际安装的插件和宿主版本没有完整记录。独立 SDK 版本未取得。
- 主样本是一份隔离、未保存、没有业务内容的文档：640 × 480 document pixels、96 DPI、1 页，包含普通文本、混排文本和小尺寸文本框。
- A-06～A-08 使用另一份隔离样本：960 × 640 document pixels、96 DPI、1 页，包含一个艺术字对象和一个未链接文本框，内容都是通用测试文字。
- 本页不保存原始脚本、原始回包、运行时对象标识、会话标识、本机路径或个人工作内容。因为没有保存图片像素，视觉结论只保留为执行时的观察，无法从本页重看。

## 证据

### A-01：应用身份、入口和 Collection

只读探针确认了该构建的应用版本和平台。在查过的入口中，`DocumentApi.getDocumentProperties` 为 `undefined`；`app.userDesktopPath` 有 getter，但应用模块顶层同名导出没有可用值；`UnitType`、`DocumentCommand` 不在脚本全局作用域内。`Collection.of(1, 2)[0]` 为 `undefined`，`.first` 和 `.at(0)` 返回首项。

这些结果只约束查过的入口和对象，不能证明同名功能在所有 native 模块或未来构建中都不存在。

<a id="a-02"></a>
### A-02：文本替换和溢出

当前 `Node.setText` wrapper 使用 `TextSelection.create(this.storyRange)`。在隔离样本上完整替换普通文本，读回通过。20px/12px 混排文本替换后合并成一个 20px run，因此普通替换不能当作保留混排格式的通用配方。

`canHideOverflow` 在查过的 wrapper 中是 getter。小尺寸文本框的 Story 字符仍然完整存在，已有执行观察显示文字溢出到框外。这不足以证明隐藏状态已经打开，也不能据此推断文字会永久丢失。改字后，行数、runs、框尺寸和可见范围仍需逐项检查。

### A-03：同步关闭

对隔离的未保存样本调用同步 `Document.close()`，然后重新枚举文档，目标样本消失。该结果只覆盖同步路径、该构建、这类隔离样本和这一次操作后检查；`closeAsync`、Promise 关闭、带未保存业务文档的关闭以及其他平台都还没有验证。

### A-04：文字节点、文本流与 Align 只读入口

观察日期和构建同上：2026-10-08，Affinity 3.3.0.4850 Win32。读取 SDK 的 `nodes.js` wrapper 时，确认了两个创建入口的签名：`ArtTextNodeDefinition.createFromStoryBuilder(position, storyBuilder)` 和 `FrameTextNodeDefinition.createFromStoryBuilder(frameBox, storyBuilder)`。这项证据只说明参数入口存在，实际创建样本见 A-06～A-08。

`commands.js` wrapper 包含 `DocumentCommand.createLinkTextFrame(srcNode, destNode)` 和 `DocumentCommand.createUnlinkTextFrame(node)`；只读枚举成员时也列出了这两个公开命令。相关原生 `DocumentCommandApi` 原型链中能看到 `createLinkTextFrameCommand` 和 `createUnlinkTextFrameCommand`。这些观察没有执行链接或取消链接，因此不验证文本流范围、内容保留或撤销效果。

当前 wrapper 和查过的 native 原型中存在水平段落 Align 入口，包括 `ParagraphAtts.alignXType`、`StoryDelta.createAlignX` 和 `DocumentCommand.createFormatText`；只读检查得到 9 个水平枚举成员。在检查范围内，没有找到框内垂直 Align 的对应读写入口。

这里的“未找到入口”只表示检查范围内缺了这个能力，不是对整个应用功能的永久否定。移动文本框、改变框尺寸或做视觉居中，也不等于设置原生垂直 Align。

水平 Align 的实际写入结果见 A-07；A-04 保留的是只读检查本身的证据边界。

框尺寸调整和自动 refit 只收集到待测建议；本构建没有操作前后的字号、文字缩放、框几何、排文和溢出对照证据，所以不提供已验证的自动适配配方。

### A-05：错误、hints 与代理边界

观察资料日期为 2026-10-08，同批应用身份探针确认是 `3.3.0.4850 Win32`。下面的回包并不都自带独立而精确的时间或构建字段；当时实际运行的代理和宿主精确版本没有完整记录，不能用当前仓库清单补填。A-05.4 的回包没有独立时间或构建字段，因此不能认定它是 A-05.3 同一请求的恢复，也不能认定是相同参数的重试。

| <a id="a-05-1"></a>A-05.1 | 探针错误引用`affinity:document`；结果文本含`Error: Failed to resolve module affinity:document`，但`isError=false` | 探针输入错误，不是业务任务失败；false也不能证明脚本成功 |

| <a id="a-05-3"></a>A-05.3 | 一次`search_sdk_hints`等待超时；收到`-32603`代理错误，文本附检查应用启动与MCP设置的通用建议，`isError=true` | 同批另有成功SDK读取记录，不能根据该通用建议判定应用未运行；超时根因未确认 |

A-05.4 里的 refit 和保持字号建议，没有本样本操作前后的状态证据；水平枚举列表也不完整，A-04 记录了 9 个成员。把“SDK 没有垂直 Align 入口”推广成“文字始终顶端排文”，或者用水平 FirstLineIndent 解释垂直 Initial Advance，都不能当作已验证配方。概念区别见[构建页](../3.3.0.4850.md#alignment)；实际水平写入结果只采用 A-07 的有限样本。

上面的通用启动建议来自历史回包。当前仓库代理按故障阶段提供诊断，只有 connect 失败才附连接检查建议；超时后，可能已经提交的调用必须先读回目标状态，不自动重放。当前传输行为以[架构说明](../../architecture.md#时间边界与恢复)、[代理实现](../../../skills/affinity-mcp/scripts/affinity-mcp-proxy.mjs)和[代理回归测试](../../../scripts/affinity-mcp-proxy.test.mjs)为依据；这不证明历史运行副本或用户已安装副本已经更新。操作是否完成，仍要同时检查内容和实际状态，不能只看 `isError`。

### A-06：同一艺术字对象中的多行与混排

观察构建和日期同上。实验先用一个采用艺术字默认样式的 `StoryBuilder`，通过 `addText` 和 `addParagraphBreak` 写入内容，再经 `ArtTextNodeDefinition.createFromStoryBuilder` 创建一个艺术字对象。全文有三行中英文，24px 和 18px 两种字号的 run 并存；对象读回和执行时渲染都确认三行仍在同一个 `ArtTextNode` 中。

实验选取显式文本子选区，把某个 18px run 内的三个 ASCII 字符做同长替换。替换后全文只发生预期变化，换行、字号 run 和对象数量都保持不变。这不证明任意长度或跨 run 的替换都能保留全部格式，也不改变 A-02 中整段混排替换失败的结论。艺术字要写多行，不必逐行、逐词创建对象；是否拆分，应由语义块和独立变换需求决定。

### A-07：单框水平Left/Centre/Right写入

在一个 400 × 220 的未链接框中，实验通过 `Selection` 的实际文本子选区、`StoryDelta.createAlignX` 和 `DocumentCommand.createFormatText` 依次切换到 Centre、Right、Left；`ParagraphAtts.alignXType` 读回依次为 1、2、0。字号 24px、文字缩放、全文和框几何保持不变，文字横向边界随模式变化；最后停在 Centre，执行时渲染确认两行文字在框内水平居中。

这证明三种水平模式在这个单框样本上可以写入，不覆盖其余六种枚举、链接框或部分段落作用范围。查过的 TextFrameInterfaceApi 和 DocumentCommandApi 原型仍未发现相应的原生垂直读写入口；水平写入成功，不能补足垂直接口的缺口。

### A-08：框中心与内容中心的反例

新建框使用默认段落样式，水平属性为 Left，文字出现在框的左上区域。框为 `(280,210,400,220)`，中心 `(480,320)` 恰好是页面中心；文字内容中心约为 `(356.73,240.55)`，两者相差约 123.27px 和 79.45px。

`getSpreadVisibleBox(false)` 返回 400 × 220 的框边界；`getExactSpreadVisibleBox(false,false)` 返回约 151.30 × 61.07 的文字边界，位置与执行时画面一致。因此框居中不能证明内容居中；经核验的实际内容边界可以用来判断位置，不必收紧固定框。

样本没有描边、效果、裁切、嵌套变换或溢出，因此不能据此给出通用的内容测量方法或自动 fit 公式。没有测试框尺寸调整；Left/左上这一观察也不代表所有模板或既有框的默认状态。水平 Centre 改变了横向排文，但没有改变内容的纵向位置；原生段落居中也不保证完整墨迹或字形主体的光学中心完全重合。

### A-09：多行段落居中与文字块水平定位

在同一构建的两个未链接、多行 `FrameTextNode` 上，实验先用显式文本子选区写入原生段落 Centre，再调用 `curvesInterface.polyPolyCurves.getExactBoundingBox(baseToSpreadTransform)`，取得 spread 坐标中的字形轮廓边界，然后按内容中心的差值做水平平移。读取这些边界不需要转曲、复制或修改轮廓。两个对象的字形中心横坐标读回一致，段落模式都是 Centre；文字、字号 run、文字缩放矩阵、框宽高和上下位置保持不变，执行时渲染确认长短行居中排文且文字块位置正确。

如果只平移对象，让合并后的外接边界中心一致，段落 Left 仍会保留，这样的结果不能算通过多行居中验收。段落内各行居中和文字块定位是两个可以同时需要的操作，必须分别检查。该样本的字形轮廓边界与 exact visible 边界一致；不推广到复杂效果、裁切、路径字、彩色字体、链接流或溢出文本。原生段落 Centre 也不承诺逐字墨迹的光学居中。没有做耗时基准，也没有做原生 GroupTransform 的 Frame 边界语义写测。

## 证据等级和限制

“样本通过”只表示在指定构建、平台、对象和操作后状态下，该用例满足要求；“只读确认”只表示入口或元数据存在；“未验证”不等于“不支持”。应用构建差异和插件版本差异要分别记录，不能把单个样本推广成对所有对象、文档状态或平台的保证。
