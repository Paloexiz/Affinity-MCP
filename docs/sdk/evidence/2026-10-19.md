# 3.3.1.4940 MacOS 合成对象证据摘要

观察日期：2026-10-19。本页只保留可复用的样本条件和操作后的结论；运行时标识、原始回包、个人路径和本机计时记录不在这里。结果范围见[构建记录](../3.3.1.4940-macos.md)。

<a id="b-01"></a>
## B-01：身份与样本隔离

- 应用自报 `Affinity 3.3.1.4940 MacOS (Oct  6 2026)`，运行插件 `0.4.3`；安装副本与对应仓库代理 hash 一致。独立 SDK 和宿主精确版本均未记录。
- 文档为自建、未保存、800 × 600 document pixels、96 DPI、单 spread；创建后读回实际尺寸。后续写入前先检查已确认的文档身份，并且只关闭各自的样本。

<a id="b-02"></a>
## B-02：三对象命令边界

基线包含六个带唯一合成标记的矩形。实验使用公共 wrapper，分别执行逐个移动、共享选区移动、compound 移动、逐个插入和批量插入三个矩形。逐个命令需要三次 undo，其余各需一次；执行相同次数的 redo 可以回到操作后的状态，再 undo 则回到操作前的状态。

每个阶段都按标记排序，比较完整的标记集合和六个变换矩阵分量。判断恢复时不单独看 `isDirty`、历史位置或撤销次数，也没有拿相反变换当作验收依据。

<a id="b-03"></a>
## B-03：500 目标与非目标状态

基线为六个保护标记和另外 500 个目标矩形。显式关闭 transform 的合并选项后，逐个移动需要 500 次 undo 才能回到完整的前态；共享选区和 compound 命令各需要一次。redo、再次 undo 仍与前后快照匹配，保护标记也包含在全部比较中。

这些结果只覆盖注明的命令、选项和历史状态，不能证明任意命令都不会合并，也不解释其他场景中的撤销不一致。快照没有穷尽颜色、效果、父级、选择状态等属性。

<a id="b-04"></a>
## B-04：预设流程与查询一致性

三轮交错对照使用同一工具入口、相同的形状定义和目标。简单移动中，分开的读取/编辑/读回流程与合并流程都核对了目标矩阵、预览内容和撤销恢复；500 个矩形的逐个/批量插入在标记和矩阵快照、渲染内容上相同，撤销后回到前态。在稳定的 1000 项集合上，500 次 `.at()` 查询和一次转成数组再索引得到相同序列。

另有一轮在应用保持运行时使用新的代理连接，用来区分资料准备和连续操作；这不能称为冷启动应用，也不是真实 Agent 的全流程对照。操作内计时、宿主调用耗时和渲染是不同的边界，仅减少 SDK 命令数量不保证端到端更快。全部样本结束后关闭文档并重新枚举，确认样本文档不再存在。

<a id="b-05"></a>
## B-05：插入命令与结果回传的独立变量

同一工具入口的三轮 2×2 样本使用两个变量：逐个/批量插入，以及全量/摘要回传。每个组合都在 10 个保护标记之外插入 500 个矩形，读取全部 510 个对象的标记和六个矩阵分量，与预期逐一比较，并使用相同的完整 spread 渲染；摘要模式只减少回传，不减少脚本内的检查。实际 undo 恢复了保护标记的前态。

命令、定义、读回和序列化分别计时，工具返回和渲染另计。两种回传模式下，批量插入的总体中位耗时都更高，样本也有明显波动；减少 SDK 命令或回包大小没有通过创建到预览的性能验收。这不解释延迟的根因，也不证明所有批量插入都会更慢，更不能据此省略检查或预览。没有把“操作后的样本状态通过”写成“性能验收通过”。

<a id="b-06"></a>
## B-06：共享选区移动的端到端边界

基线为六个保护标记和 500 个目标矩形。五组配对交替调整先后顺序，分别在一个脚本内逐个移动目标，或对共享选区执行同一位移；两条路径都保留文档身份守卫、全部标记与六个矩阵分量的预期值比较，以及完整 spread 渲染。两种路径的图像内容一致，逐个路径的 500 次 undo 和选区路径的一次 undo 都恢复了前态。

这五组记录的是编辑调用与完整渲染调用的耗时之和，不包含两次调用之间的宿主编排时间。共享选区在四组较快、一组较慢，中位数下降。另有三组相同任务使用连续计时，从编辑调用前一直到完整渲染返回，中间包含解析和校验；三组共享选区都较快，连续耗时中位数下降，状态、图像和 undo 检查仍然通过。

结论只限这个预设移动任务和本页构建。计时不含首次资料准备、夹具建立、撤销清理，也不含真实 Agent 读取新旧 Skill 的决策耗时；没有覆盖任意嵌套目标或业务工程，也不能移用到 B-05 的插入任务。执行时比较完整图像和恢复值，原始归档保留参考图像和逐轮检查结果，没有逐轮保存全部图像和 undo 回包。三个用例的自建未保存样本都已关闭，重新枚举后确认移除。

<a id="b-07"></a>
## B-07：独立文档上的创建到预览对照

每轮使用独立自建文档和 10 个保护标记，在夹具建立、前态确认后才开始任务计时；写入脚本仍在计时内导入模块，并检查 `Document.current.sessionUuid`。逐个或批量插入 500 个矩形后，全量回传并比较 510 个标记和六个矩阵分量，再取得同范围的完整 spread 图像比较内容。计时到图像比较完成时结束；实际 500 次或一次 undo、关闭自身文档和重新枚举都在其后分别记录，没有把清理时间算进创建耗时。

同一宿主工具入口预设三组配对，顺序为逐个/批量、批量/逐个、逐个/批量。三组都是批量路径的创建到预览耗时较短，中位耗时下降；状态、逐轮完整图像和撤销回包都保留，保护标记全部恢复，文档也全部清理。另有一个使用相同完整 Plugin 的诊断驱动器，同样完成三组独立文档对照，但两种入口的绝对耗时不能混为同一组结果。

分段诊断在部分慢调用中定位到 `DocumentApi.getCurrent()` 等待；额外的只读检查没有消除所有后续等待，改用枚举后精确 UUID 绑定也没有改善同任务的中位耗时，所以这些做法都没有作为提速配方采用。独立文档的结果不改写 B-05 的旧观察，也不能证明该 getter 在应用内部的等待机制，或证明任意清理后应用已经空闲。收益只适用于本页的简单对象、既定验证范围和三组配对；不包括首次准备、创建文档夹具、清理或 Agent 决策，也不构成“批量插入默认更快”的结论。

<a id="b-08"></a>
## B-08：扩大创建样本的稳定性边界

另预先固定 12 组配对，分两块并平衡逐个先做与批量先做的顺序，共使用 24 个独立自建文档。B-07 的三组只作探索记录，不并入本组。任务范围和验证方式保持一致：计时内包含模块导入、当前文档身份守卫、500 对象创建、全量回传和 510 个标记/矩阵检查，直到完整图像比较完成；夹具准备及实际撤销/关闭另外记录。24 张图像都与外部参考逐字节一致，实际 500 次或一次 undo 都恢复了 10 个保护标记，全部样本文档关闭后重新枚举确认移除。

12 组中，批量路径九组较快、三组较慢；逐个先做时三快三慢，批量先做时六组较快。总体中位数仍偏向批量，但顺序分层后的方向不同，按两个中位数之比计算的区间也没有排除反向收益。配对差和这个比值是不同指标，不能互相替代；长等待被完整保留，没有靠剔除离群样本或加入旧三组来强化结果。

逐个与批量的总耗时中位数分别为 4972.5ms、4607ms。按原口径 `1−median(B)/median(S)` 计算，降幅为 7.35%，95% bootstrap 区间为 −9.95% 至 18.35%。配对差 `Δ=S−B` 的均值为 976.75ms、中位数为 467ms；两者的区间分别为 [83.67, 2087]ms 和 [223, 852]ms。配对改善 `median(1−B/S)` 为 8.68%，区间为 [3.86%, 16.68%]。区间使用固定种子 20000、20000 次整对重采样，在块×顺序四格内各保留三对，以线性插值的百分位法取 95% 区间；双侧精确符号检验 p=0.146。每格只有三对，而且顺序有差异，所以正的配对区间不能单独作为稳定收益的确认依据。

<a id="b-09"></a>
## B-09：同次编辑回传完整 PNG 的受限预览路径

这一组使用相同的应用构建，安装插件为 `0.4.3`。实验在一个独立子代理的同一 Codex/functions 工具上下文里预设 12 对、共 24 个独立合成文档。两侧都使用相同的 batch500 创建、800 × 600 document pixels、96 DPI、10 个保护标记，以及相同的完整名称/六矩阵和选区检查。基线随后单独调用 `render_spread`；候选在原 `execute_script` 内用公开的同步 PNG/CurrentSpread 导出，通过 `File.readAll(...).toString('base64')` 读回并删除本次唯一的临时文件，确认检查字段和选区不变后，再由宿主显式转发完整原生图像。已有的 Desktop 文件权限没有改变，也拒绝覆盖预存输出；这不是把两次 Affinity 工具调用包装成一次。

计时从发出 create500 脚本前开始，到完整图像通过宿主 `image` 和 awaited `yield_control()` 实际交付后结束。计时包含导入、UUID 绑定、对象/选区检查、全部候选文件工作和预览回传；不含文档/夹具准备、诊断落盘、稍后的离线像素 oracle、undo/close 或模型决策。计时使用 `Date.now()` 墙钟，没有测量前端绘制确认；这个终点与 B-08 的“计至图像比较完成”不同，不能混为同一指标。这里只验证规定流程，不验证自主 Agent 读取 Skill 后的整体效率。

两侧 24 个有效样本都核对了 510 个名称及六矩阵、十个保护标记和最终 500 选区；12 张基线 JPEG 完整解码为 109087 字节，与既有参考相同；12 张候选 PNG 都是 800 × 600，480000 个 RGB 像素与合成真值完全相同。JPEG 和 PNG 编码不同，因此不作字节或元数据等价的结论。每一侧实际执行一次 undo，恢复了十个基线标记及其选区，只关闭自身样本并确认文档清单恢复；候选临时文件在返回前清除，结束后再次只读确认全部样本文件不存在。有效样本通过，不代表所有准备尝试或任意节点属性都已经验证。

全部长等待和唯一一个反向配对都保留；基线/候选的 12 次任务耗时总和为 56465/34921ms，范围分别是 3428～8127ms 和 1928～5890ms。逐对改善中位数为 34.80%（95% 区间 28.09%～45.36%），配对差中位数为 1404ms（1042.5～1941.5ms），它们与上表的两个中位数之比是不同估计量。前六/后六对的中位比改善分别为 39.06%/44.21%，只作描述。

顺序是固定平衡的，并非随机，每层六对。区间使用固定种子 20000、20000 次顺序分层整对重采样，层内样本数保持不变，采用线性分位数法。没有合并 B-07/B-08、其他入口、工具栏或可行性样本。结论只支持该小画幅矩形任务中减少一次预览往返的实际收益，不能推出 PNG 在复杂场景更小/更快、跨平台固定增益、任意宿主连接故障已恢复，或 `getCurrent()` 的应用内部阻塞已修复。操作门槛见[单调用预览](../../../skills/affinity-mcp/references/scripting-pitfalls.md#single-call-preview)。
